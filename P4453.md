# Abstract # {- .unlisted}

This paper responds to Irish NB comment IE-133 concerning memory allocation with senders/receivers.

# The concern

The Irish NB provided the following comment during C\++26 ballot voting:

> The Irish NB did not reach consensus on senders/receivers. Some concerns:
>
> • Senders/receivers allocate implicitly using std::allocator, and a task's default task_scheduler can allocate using a default allocator even when the task is given an allocator.
>
> • Parallel scheduler backends get storage of unspecified size and no guaranteed allocator, so may allocate per operation.
> 
> This is unsuitable where allocation must be controlled, such as on embedded platforms.
>
> The earlier version, P2300R10, had none of these issues.

# On the parallel scheduler's allocator #

## Conceptual model

The main scenario for which the parallel scheduler (formerly the system scheduler) [@P2079R10] was designed is:

- parallel work uses a shared execution context, which manages execution resources to avoid oversubscription;
- multiple applications might use this context at once, allowing worker management to account for their combined demand;
- by default, the backend is intended to use OS-provided execution facilities, such as Windows Thread Pool or Grand Central Dispatch, where available.

To support custom workflows, we also let applications replace the default mechanism and register their own backend.

The implementation has two parts:

- backend: the implementation of the system execution context;
- frontend: the standard library implementation that calls the backend.

The backend implements the interface described in the `parallel_scheduler_replacement` namespace, and the frontend communicates with it through this interface. Because the backend can be replaced, this communication crosses a type-erased boundary.

## Who should control which allocations? An analogy

Let us consider a similar case: a `static_thread_pool` and its scheduler. NVIDIA's stdexec library [@stdexec] provides an implementation. Do we need an allocator? If so, where?

If we look at NVIDIA's `static_thread_pool` implementation, we see that the client cannot provide an allocator for a regular scheduling operation:

- obtaining a scheduler from `static_thread_pool` takes no client-provided allocator argument;
- the API of `std::execution::schedule` does not require an allocator;
- the implementation does not use an allocator obtained from the receiver's environment.

For bulk scheduling, NVIDIA's `static_thread_pool` implementation uses an allocator to create storage for the task descriptors. This allocator is internal; it is not obtained from the receiver's environment.

Scheduling individual items still requires storage for their operation states. Where does this come from? The scheduling operation state is embedded in the parent operation state object. Most of the time, this is just stack space. The size of the scheduling operation state is statically known, and there is no type-erased boundary between frontend and backend. We can therefore let the composition of operation states provide the needed storage.

A parallel scheduler resembles a thread pool, with the main difference that the parallel scheduler's context is intended to be shared between applications. We aim for similar allocator behavior. The backend knows its internal storage requirements and can manage that storage together with its execution resources. For example, it can maintain a pool of task descriptors and reuse them across operations. This allows the allocation strategy to be chosen for the backend as a whole.

Thus, in the spirit of a regular thread pool, we should not need a client-provided allocator for the parallel scheduler.

## Storage space for the internal operation state

If we do not need a client-provided allocator, why do the backend's scheduling methods take a `std::span<std::byte>` parameter?

Unlike a `static_thread_pool`, a parallel scheduler requires type erasure between the frontend and the backend. The size of the backend's operation state is therefore unknown to the frontend, preventing direct composition with the parent's operation state.

To solve this issue, we allow the parent operation state to provide storage for the backend to use as it sees fit. If the backend operation state fits in that storage, it can be nested in the parent operation state, just as with `static_thread_pool`. No extra allocation is needed for that state.

If the backend operation state cannot be placed in the space provided by the frontend, then it must obtain storage elsewhere. This is the responsibility of the backend. Different platforms might implement the allocation in different ways, optimizing for different things (speed, space, etc).

## Embedded platforms

Embedded platforms typically need a dedicated backend, which is likely to be provided by the application itself. Thus, **the application has full control over the required memory allocation**.

## In the future, can we add allocators?

Yes. The query mechanism in `receiver_proxy` allows us to add allocator support in future editions of the standard.

We took an incremental approach, specifying a minimal set of operations while providing a query mechanism for future extensions. A backend can query whether the receiver exposes an allocator, even if that query is not specified in the standard. This also allows non-standard extensions for particular platforms (e.g., embedded platforms).

However, there are costs to this. First, the query crosses the type-erased frontend/backend boundary. When additional storage is needed, querying the frontend has a performance cost even if the receiver's environment provides no allocator. Second, the allocator itself also needs a type-erased representation, such as `std::pmr::polymorphic_allocator<>`.

This is why we did not want to mandate these costs for all uses of the parallel scheduler without strong signals from the community that receiver-provided allocators are needed.

## Bottom line

We think that the current specification of the parallel scheduler is a good compromise that meets requirements from different industries. On embedded platforms, the backend can be fully customized to use the appropriate allocation strategy. In other domains, users do not have to pay for custom allocation logic when they do not need it.

If this approach proves insufficient, we can extend it in C\++29 or later.
