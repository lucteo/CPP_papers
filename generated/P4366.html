Abstract

We have decades of experience showing that programming with locks is hard, error-prone, and often inefficient. Senders/receivers provide an asynchronous alternative for expressing concurrent abstractions. Unfortunately, C++26 does not provide primitives for dealing with non-local concurrency, nor does it provide a transition path for applications that currently use locks to move to asynchronous applications relying on senders/receivers.

This paper is the first in a series that aims to bridge that gap. It proposes serial_gate , an asynchronous alternative to a mutex. Because mutexes are the most widely used legacy synchronization primitive, adding such a primitive provides an important first step.

2 Introduction

[P2300R10] describes the framework for senders/receivers and introduces primitives for handling concurrency. These primitives operate locally: they connect senders that appear in the same scope. However, concurrent behavior may require different parts of an application to interact. This is non-local concurrency, for which C++26 currently lacks good solutions. The closest facility is counting_scope , which does not require the senders spawned within it to be local; however, it does not allow us to impose constraints between different work items.

[P4215R0] proposed a vision for primitives that solve non-local concurrency and described a principled approach to solving it.

That approach is based on three pillars:

  • The essence of concurrency: concurrency can be seen as a strict partial ordering over the execution of work items. If we focus on the required happens-before relations, and on the absence of such relations, we can model any concurrent problem.
  • Safety and progress: taking ideas from [P4214R0], a good solution would guarantee safety and progress for the program (under certain assumptions) and make it hard for users to misuse the features.
  • Classical synchronization primitives: taking inspiration from them would provide asynchronous primitives that let us build all types of concurrent programs and make the transition from old-style concurrency easier.

Following these principles, [P4215R0] proposes a first set of non-local concurrency primitives to be added to C++:

Proposed primitive
Corresponding legacy primitive
serial_gate mutex
read_write_gate shared_mutex
capacity_gate counting_semaphore
readiness_gate condition_variable
completion_gate latch
phase_gate barrier

The same ideas also suggest how we can go beyond these primitives to provide more advanced facilities for dealing with non-local concurrency:

  • A keyed_serial_gate serializes operations that have the same key, while allowing operations with different keys to proceed concurrently.
  • A budget_gate admits operations while a resource budget is available; unlike capacity_gate , different operations may consume different amounts.
  • A priority_gate admits pending operations according to priority.
  • A deadline_gate admits, orders, or stops pending operations according to deadlines.
  • A rate_gate admits operations according to a time-based rate rather than a concurrency bound.
  • A throttle_gate spaces out admitted operations, for example by ensuring a minimum interval between starts.
  • A backpressure_gate admits upstream work only when downstream capacity is available.
  • A coalescing_gate combines compatible pending operations before admission.
  • A latest_only_gate retains only the most recent pending operation and stops or discards older pending operations that have been superseded.

We prefer using the word gate in these names because it suggests admission into a region of work and avoids implying blocking threads or legacy synchronization mechanics. It also resonates with the idea of adding concurrency constraints. [P4215R0] contains a brief exploration of different possible names.

This paper focuses on the first step in this journey: serial_gate .

A serial gate is a primitive that allows work items to execute asynchronously while maintaining mutual exclusion. It is essentially a task queue from which at most one item can execute at a time.

3 Examples

Below, we show several examples of using a serial_gate . For brevity, we assume that spawned senders either complete without set_error or handle errors before being passed to spawn , and that the enclosing program eventually joins the counting_scope .

3.1 Protecting non-thread-safe state

A serial_gate can protect state accessed by asynchronous operations. Unlike a mutex , entering the protected region does not block the current thread of execution; it suspends the operation until it can make progress.

struct cache {
  void insert(record);
};

serial_gate cache_gate;
cache c;
std::execution::counting_scope scope;

void on_record(record r) {
  auto update
    = std::execution::just(std::move(r))
    | std::execution::then([&](record r) noexcept {
      c.insert(std::move(r));
    });

  auto protected_update =
    std::execution::within(cache_gate.acquire(), std::move(update));

  std::execution::spawn(std::move(protected_update), scope.get_token());
}

In this example, cache_gate serializes all calls to cache::insert , even when multiple records are received concurrently.

We envision another abstraction, serialized_access<T> , that couples a value with the serial_gate used to access it. This abstraction would simplify the example. We will propose it in a dedicated paper.

3.2 Executing work after protected work completes

Sometimes, we need to perform additional work after the protected operation completes. We might not want to put that additional work in the protected region, because it could delay other work that needs protection.

For example, suppose that we want to perform some logging after updating the cache. We can express this as follows:

void on_record(record r) {
  auto update
    = std::execution::just(std::move(r))
    | std::execution::then([&](record r) noexcept {
      c.insert(r);
      return r;
    });

  auto protected_update =
    std::execution::within(cache_gate.acquire(), std::move(update));

  // NEW
  auto with_logging
    = std::move(protected_update)
    | std::execution::then(perform_logging_after_update);

  std::execution::spawn(std::move(with_logging), scope.get_token());
}

3.3 Serializing protocol operations

Some asynchronous resources support many callers but require only one operation to be active at a time. For example, a connection might require requests to be sent and responses to be consumed serially, even when callers enqueue work concurrently.

serial_gate connection_gate;
connection conn;
std::execution::counting_scope scope;

void submit_request(request req) {
  prepare(req); // does not need exclusive access to conn

  auto transaction
    = send_request(conn, std::move(req))
    | std::execution::let_value([&] (request req) noexcept  {
      return read_response(std::move(req), conn);
    })
    | std::execution::then(process_response);

  auto protected_transaction =
    std::execution::within(connection_gate.acquire(), std::move(transaction));

  std::execution::spawn(std::move(protected_transaction), scope.get_token());

  continue_after_submit(); // does not wait for the transaction to finish
}

The serial_gate constrains only the transaction that uses conn . Work performed before submitting the transaction and work performed after submission are not forced to wait for the protected operation to complete.

3.4 Saving documents

Suppose that an application saves documents asynchronously, either to disk or to the cloud. In a text editor, saving might be triggered by events such as keystrokes or at regular intervals. We might not want multiple document-save operations to run concurrently, so we can route each save through a serial_gate :

serial_gate gate;
std::execution::counting_scope scope;

void trigger_save(document d) {
  auto work
    = std::execution::just(std::move(d))
    | std::execution::let_value(save_async);

  auto protected_work =
    std::execution::within(gate.acquire(), std::move(work));

  std::execution::spawn(std::move(protected_work), scope.get_token());
}

This guarantees that two save_async operations will not run concurrently.

3.5 Saving documents if not already in progress

In the preceding example, a save might be triggered while another save operation is in progress. We might want to skip the new save rather than queue it. We can use the gate’s speculative-execution capability:

serial_gate gate;
std::execution::counting_scope scope;

void trigger_save(document d) {
  auto work
    = std::execution::just(std::move(d))
    | std::execution::let_value(save_async);

  auto protected_work =
    std::execution::within(gate.try_acquire(), std::move(work)); // UPDATE: speculative execution

  // NEW: ignore the error
  auto handle_error
    = std::move(protected_work)
    | std::execution::upon_error([](busy_error) noexcept {});

  std::execution::spawn(std::move(handle_error), scope.get_token());
}

If work is already admitted to the gate, gate.try_acquire() completes with busy_error , and the protected work is not executed.

4 API

We propose adding the following API to std::execution :

/// Indicates that the gate is busy, i.e., the `try_` operation failed.
struct busy_error : std::exception {};

/// A gate that allows maximum one work item to be executed at a time.
struct serial_gate {
  serial_gate();
  ~serial_gate();
  serial_gate(const serial_gate&) = delete;
  serial_gate(serial_gate&&)      = delete;

  /// Returns an enter-scope sender that serializes protected work through `*this`.
  std::execution::enter_scope_sender auto acquire() noexcept;

  /// Returns an enter-scope sender that tries to execute protected work through `*this`.
  ///
  /// If the gate cannot be reserved immediately, the enter scope completes with
  /// `set_error(busy_error{})`; otherwise it behaves like acquire().
  std::execution::enter_scope_sender auto try_acquire() noexcept;
};

A serial_gate provides these synchronization guarantees:

  • completion/release of one admitted work item synchronizes with admission/start of the next;
  • a successful try_acquire() has the same synchronization guarantee;
  • a failed try_acquire() establishes no synchronization.

5 Design-space discussions

5.1 Using asynchronous scopes

This paper is based on [P3955R1], which introduces the idea of asynchronous scopes. Executing protected work for a serial_gate maps directly to this idea: the protected work runs within an asynchronous scope obtained from the gate.

Implementing the enter the gate and leave the gate operations manually seems inferior to this solution.

There is, however, another alternative, inspired by the API of counting_scope :

struct serial_gate {
  struct token; // models std::execution::scope_token

  token get_token() noexcept;
};

At the usage site, instead of using std::execution::within(gate.acquire(), work) , we could use std::execution::associate(work, gate.get_token()) .

Syntactically, the difference would be small. Semantically, however, gates do not fully match the scopes required by scope_token . The current C++26 standard says:

The scope_token concept defines the requirements on a type Token that can be used to create associations between senders and an async scope. Every object of type Token is associated with an async scope that is referred to as its associated scope.

Gates are not async scopes, so they do not properly fit the scope_token schema.

Moreover, pursuing this design might tempt users to write std::execution::spawn(work, gate.get_token()) . That would be problematic: it would add a work item to the scope without anyone tracking its lifetime, introducing safety issues.

5.2 Admission and cancellation

When an acquire operation is started, the gate either admits it immediately or registers it as a waiting operation. A waiting operation does not occupy the gate until it is admitted. From the perspective of work executed in a serial gate, we say that the gate is acquired while the work is running and released immediately after the work completes.

Once an operation has been admitted, the gate remains occupied until the exit sender produced by the admission operation completes. This remains true if the protected work completes with set_value , set_error , or set_stopped .

If an admitted operation completes with set_stopped , it has no effect on follow-up admitted items.

A waiting operation will eventually be admitted to the gate; there is no way to cancel the admission. Once the operation runs, it can detect cancellation and complete immediately, but this still requires the operation to be admitted to the gate.

This design intentionally does not cancel waiting acquisitions. Consequently, canceling an operation does not remove it from the gate’s waiting set, and shutdown may have to admit canceled operations before the gate can be destroyed.

5.3 Speculative execution

As with the classic try_lock facility, gates can support speculative execution. Sometimes an operation is useful only if it can start immediately. If the non-local constraint would force the operation to wait, the program may prefer to skip that operation and continue with other work.

To handle this case, we envision try_acquire() . When started, try_acquire() attempts to reserve the gate without registering the operation as a waiter. If the reservation cannot be made immediately, it completes with set_error(busy_error{}) . On success, it has the same semantics as acquire() . try_acquire() either admits the work immediately or fails.

An alternative considered here was to send a set_stopped() signal instead of set_error(busy_error) ; in fact, [P4215R0] proposed this. During the SG1 discussions in Brno, it was argued that sending a dedicated error type would be better because the protected work might want to distinguish this busy condition from the entire work being canceled. In response, we changed the design to incorporate this feedback.

5.4 Fairness

Work items executed within the serial gate will be backed by a task queue, but we do not specify their execution order. This is intentional.

We recognize that some users might want fairness guarantees from a serial gate, meaning that work items are executed in the order they are submitted. However, we cannot confidently say that this represents the vast majority of our users. Guaranteeing fairness typically introduces performance penalties, and we do not want to commit to this path.

If we later find that a fair serial gate is needed, we can add a new fair_serial_queue or retrofit fairness into the current API. We defer this addition until we know that it is required.

Until then, we allow implementers to provide the best strategy that fits their customer base.

5.5 No implicit scheduler transition

One question that arises is where an admitted operation is started. A serial_gate intentionally does not combine admission policy with execution-resource selection and therefore introduces no implicit scheduler transition.

The sender returned by acquire() does not guarantee a completion scheduler. An immediately admitted acquisition may complete inline during start. A queued acquisition may complete on the execution agent that makes the gate available. Consequently, unless the protected sender performs an explicit transition, it may be started on that execution agent.

Adding a scheduler to serial_gate would introduce several independent policy choices. The scheduler could belong to the gate or to each acquisition. Scheduling could happen before reserving the gate, in which case another operation may be admitted first, or after reserving it, in which case the gate remains unavailable while the scheduler is reached. The latter choice also requires scheduler failure and cancellation to relinquish the reservation correctly. A scheduler could control where the protected sender is started, but this would not determine where that sender subsequently executes or completes. These choices are execution policies rather than properties of mutual exclusion.

try_acquire() makes the ordering of admission and scheduling particularly significant. If the scheduler transition happens first, availability is tested only after that transition, rather than when the acquire operation is started. If the gate is reserved first, a successful acquisition may not complete until later, the gate remains unavailable during the transition, and scheduling failure or cancellation must relinquish the reservation correctly.

Keeping the gate scheduler-neutral is consistent with the [P2300R10] principle that execution-resource transitions are explicit. When a protected sender must be started on a particular scheduler, this can be expressed directly:

auto w = within(
    gate.acquire(),
    starts_on(my_scheduler, work));

Here the gate is acquired before the transition to my_scheduler ; the scheduling delay is therefore part of the protected region. If the continuation following the protected region must execute on a particular scheduler, that is a separate transition:

auto w =
    within(gate.acquire(), starts_on(inside_scheduler, work))
  | continues_on(outside_scheduler);

When one protected operation completes, releasing the gate may immediately admit another queued operation. Consequently, if work1 completes on a particular execution resource, the gate may start a queued work2 on that same execution resource. This cross-operation propagation of execution context is an intentional consequence of scheduler neutrality. A caller that does not want its protected operation to be started by the preceding operation should introduce an explicit transition inside the protected region, as in the first example above.

5.6 Protected data

Like the proposed synchronized_value [P0290R4] or Rust’s Mutex , we might want to protect data used in an asynchronous world. We designed serial_gate to support this use case. A facility for this use case is proposed in P4368R0?.

5.7 Do we need concepts?

Because we envision adding other types of gates to the standard, we have considered whether the gates need a concept.

Although some gates have similar interfaces, we found no good reason to introduce a concept. As with containers and algorithms, which interact through iterators, algorithms built on gates can interact through the exposed std::execution::enter_scope_sender (see [P3955R0]).

5.8 More scope algorithms

Following [P3955R0], we might want to use more than just the within algorithm. We might use enter_scopes or nest_scopes when a particular work item needs to enter multiple scopes.

This might be useful when a work item needs to execute as part of multiple gates, similar to taking multiple locks for an operation. Although this is possible, the scheme would have problems similar to those of multiple locks in synchronous code. Instead of a deadlock, however, we would have a livelock.

This illustrates that the design of the serial gate is flexible enough to work with other scope algorithms.

5.9 Making it synchronous

Although senders/receivers aim to limit the number of required synchronous calls, synchronous calls are sometimes useful. This raises the question of whether a serial gate can be used in a synchronous context. For example, an application might be moving from legacy primitives to senders/receivers and use a serial gate instead of a mutex while still having one context that cannot yet be made asynchronous.

We can use a serial gate in a synchronous context by applying sync_wait to the resulting work:

std::this_thread::sync_wait(std::execution::within(gate.acquire(), work));

5.10 Why not use a single-threaded scheduler?

Using a single-threaded scheduler is an alternative often considered for serializing work. However, it does not work in the general case.

A single-threaded scheduler can serialize callbacks submitted to that scheduler, but it does not by itself impose serialization on arbitrary sender work that is submitted from other execution agents or whose asynchronous operation spans external events and resumes elsewhere. A serial_gate imposes the constraint on the sender’s protected operation independently of the execution resource used by that operation.

6 Safety and progress

Following the ideas from [P4214R0], we assess the correctness of an application that uses serial_gate with respect to two aspects: safety (regarding problem-domain properties) and progress.

6.1 Safety

Using serial_gate has two main preconditions:

  • all work that runs through serial_gate needs to be safe (with respect to the application’s safety properties), regardless of the execution order of that work;
  • all work needs to be completed before the serial_gate object is destroyed.

The first precondition concerns external code and must be reasoned about outside serial_gate ; serial_gate cannot enforce it.

The second precondition is enforced by serial_gate . On destruction, std::terminate() is called if any work remains incomplete.

serial_gate is implemented on top of a task queue. An implementation can easily guarantee common safety properties for the queue itself, such as memory safety, thread safety, and arithmetic safety. Unless the application has safety requirements that rule out specific queue implementations (which rarely happens in practice), the implementation can ensure that the underlying implementation of serial_gate is safe with respect to the application’s safety properties.

Deadlocks are a specific safety concern in concurrent code. Because serial_gate is not a blocking primitive, one cannot use it directly to create a deadlock.

We assume that the application has safety requirements that rule out specific queue implementations, and that no-halting is not such a safety requirement.

Together, these observations suggest that adding serial_gate to an application cannot lead to safety violations. If the application code is safe, adding serial_gate preserves that safety.

6.2 Progress

To guarantee progress, a serial queue requires certain preconditions:

  • each work item, when executed, eventually completes;
  • there is a finite amount of work that is submitted to the queue;
  • at least one work item is capable of producing the final observable answer;
  • at least one such work item is eventually submitted to the queue.

For serial_gate , a suitable implementation can prove that all submitted work is executed when the amount of work is bounded.

Thus, if preconditions hold, adding a serial_gate to the application preserves progress.

If both safety and progress hold, then, for sufficiently detailed safety properties, we achieve correctness.

If the preconditions for progress are violated, we might still reach live-locks. A serial gate cannot detect or prevent them.
